envd requirements 경로 이탈과 TOCTOU

requirements 파일을 호스트에서 읽는 코드를 따라가다가 경로 경계가 빠진 것을 확인했습니다. 첫 수정 뒤에도 파일을 검사하는 시점과 여는 시점 사이에 빈틈이 남아 있어 다시 전달했습니다.

대상

심각도

읽는 파일이 어디에 있는가

install.python_packages(requirements=...)에 파일 경로를 넘기면, envd는 빌드 명령을 만들기 전에 그 파일을 호스트에서 읽습니다. 내용을 의존성 목록으로 해석한 다음, 조건에 따라 설치 단계에 넣는 구조입니다. 이 흐름은 호스트 파일을 직접 만지기 때문에 경로가 빌드 컨텍스트 안에 있는지가 중요했습니다.

처음 코드를 볼 때는 pip 명령을 만드는 부분보다 파일을 여는 부분을 먼저 따라갔습니다. requirements로 받은 경로가 컨텍스트 안에 머무는지 확인하는 단계가 없었습니다. 빌드 입력에 영향을 줄 수 있는 사람이 바깥 파일을 가리키면, envd 실행 권한으로 그 파일을 읽는 흐름이었습니다.

호스트에서 일어나는 일 · 흐름을 줄여 쓴 예시
requirements 경로를 받음
→ 해당 경로의 파일을 호스트에서 엶
→ 각 줄을 의존성 항목으로 해석
→ 설치 단계와 디버그 로그에 반영될 수 있음

호스트에서 requirements를 읽는 동작은 be78326에서 들어왔고, 영향을 받는 최초 릴리스는 0.3.38로 정리됐습니다. 읽은 내용이 무엇인지에 따라 로그나 빌드 단계 메타데이터에 일부 정보가 남을 수 있지만, 아무 파일이나 무조건 유출된다는 뜻은 아닙니다.

첫 패치를 다시 읽었다

첫 수정 f576c92는 입력 경로를 검증하고, filepath.EvalSymlinks로 링크를 해석한 뒤 빌드 컨텍스트 안인지 확인했습니다. 일반적인 경로 이탈은 여기서 걸러집니다. 이 변경이 1.3.5에 들어간 뒤 수정된 흐름을 다시 읽었습니다.

남아 있던 문제는 확인한 파일과 실제로 여는 파일을 묶어 두지 않았다는 점입니다. EvalSymlinks가 돌려주는 것은 그 순간의 경로명입니다. 그 뒤 os.Open이 경로를 다시 따라갈 때 관련 디렉터리나 링크가 바뀌면, 검사를 통과한 파일과 다른 파일을 열 수 있습니다.

1.3.5의 검사와 사용 사이 · 설명용 의사 코드
resolved, err := filepath.EvalSymlinks(requirementsPath)
if err != nil { return err }
if err := checkWithinBuildContext(resolved); err != nil { return err }

// 검사 이후 관련 경로가 바뀔 수 있음
file, err := os.Open(resolved) // 파일 열 때 다시 경로를 조회

checkWithinBuildContext는 실제 함수명이 아니라 설명용 이름입니다. 이런 검사 시점과 사용 시점의 차이를 TOCTOU라고 부릅니다. 관련 경로를 동시에 바꿀 수 있어야 하는 조건이 붙지만, 첫 패치만으로는 경계가 완전히 고정되지 않았습니다. 이 부분을 추가로 제보해 1.3.5도 영향받는 버전으로 남았습니다.

경로 대신 디렉터리를 기준으로

두 번째 수정 9d575b3은 파일을 여는 방법 자체를 바꿨습니다. os.OpenRoot로 빌드 컨텍스트 디렉터리의 핸들을 잡고, Root.Open으로 그 안의 파일을 엽니다. 문자열로 된 경로가 나중에도 같은 대상을 가리킬 거라고 믿는 대신, 열린 디렉터리를 기준으로 파일을 찾는 방식입니다. 1.3.6에 포함됐습니다.

루트 핸들을 기준으로 읽기 · 설명용 코드
root, err := os.OpenRoot(buildContext)
if err != nil { return err }
defer root.Close()

file, err := root.Open(requirementsPath)

회귀 테스트는 차이를 눈에 보이게 만들었습니다. 먼저 컨텍스트 디렉터리를 열어 둡니다. 그 디렉터리를 다른 곳으로 옮긴 뒤, 원래 위치에 내용이 다른 디렉터리를 새로 만듭니다. 경로명으로 다시 읽으면 새 디렉터리의 파일을 보지만, 기존 루트 핸들로 읽으면 처음 열어 둔 디렉터리의 파일을 봅니다. ‘검사했던 대상’을 유지한다는 의미가 여기서 분명해졌습니다.

어디까지 확인했는가

처음 문제는 빌드 입력을 제어할 수 있는 사람이 컨텍스트 밖 파일을 읽게 만들 수 있다는 것입니다. 첫 수정 뒤 남은 레이스는 거기에 더해 관련 파일시스템 경로를 동시에 바꿀 수 있어야 합니다. 두 경우 모두 실제로 읽을 수 있는 범위는 envd 프로세스 권한에 묶입니다.

회귀 테스트가 보여준 것은 ‘루트 핸들은 원래 디렉터리를 계속 가리킨다’는 성질입니다. 호스트 파일 내용이 외부로 빠져나가는 전 과정을 재현한 테스트라고 적으면 확인 범위를 넘습니다. requirements 파싱 결과에 따라 로그나 빌드 단계 메타데이터에 정보가 드러날 수 있다는 영향으로 구분해 두었습니다.

결국 한 파일을 두 번 읽어 본 기록이 됐습니다. 처음에는 경계 검사가 없다는 점을, 1.3.5가 나온 뒤에는 그 검사가 실제 파일 열기까지 이어지지 않는다는 점을 찾았습니다. 그 결과 수정도 1.3.5와 1.3.6, 두 번에 걸쳐 들어갔습니다.
