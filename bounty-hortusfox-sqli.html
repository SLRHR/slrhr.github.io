HortusFox 설정값에서 찾은 SQL Injection

관리자 설정을 켜고 끄는 요청을 따라가다가, 요청값이 쿼리의 컬럼 이름으로 넘어가는 것을 확인했습니다. 어디서 입력되고 어떤 결과로 이어졌는지 정리했습니다.

대상
HortusFox ≤ 6.2
심각도

분류

설정 이름을 따라가 보니

관리자 화면에는 불리언 설정을 바꾸는 기능이 있습니다. 요청을 받는 라우트부터 컨트롤러, 모델까지 name이 어디로 가는지 차례대로 봤습니다. 라우트는 /admin/environment/boolean/toggle이고, 컨트롤러는 쿼리 문자열의 name을 읽어 AppModel::updateSingle()에 넘깁니다.

여기서 name은 설정의 값이 아니라 ‘어떤 설정을 바꿀지’ 지정하는 이름입니다. 일반적으로는 서버가 허용한 몇 개의 설정명 중 하나여야 합니다. 그런데 이 경로에서는 그 목록과 대조하지 않았습니다.

입력되는 자리

app/controller/admin.php
public function toggle_boolean_value($request)
{
    $name = $request->params()->query('name');
    $value = (bool) app($name, 0);
    $value = !$value;

    AppModel::updateSingle($name, $value);
}

실제 파일은 app/controller/admin.php입니다. 위 코드는 관련 줄만 추려 놓은 것입니다. name으로 현재 설정을 읽어 값을 뒤집는 동작 자체는 단순하지만, 그 이름을 다시 SQL에 넣는 다음 단계가 중요했습니다.

값은 묶었지만, 컬럼명은 그대로였다

app/models/AppModel.php
public static function updateSingle($name, $value)
{
    static::raw(
        'UPDATE `@THIS` SET ' . $name . ' = ?',
        [$value]
    );
}

app/models/AppModel.php의 updateSingle()을 보니 차이가 분명했습니다. 바꿀 값인 $value는 ?에 바인딩됩니다. 반면 $name은 SET 뒤에 문자열로 붙습니다. 파라미터 바인딩은 데이터 값에는 적용되지만 SQL 식별자, 즉 컬럼 이름을 안전하게 고르는 일까지 해 주지는 않습니다.

허용 목록이 없으니 요청한 이름이 단순 컬럼명인지, SQL 구조를 바꾸는 표현식인지 모델에서 구별하지 못합니다. 이 부분을 보고 같은 함수를 호출하는 다른 곳도 검색했습니다. 다른 호출은 고정된 이름을 넘겼고, 요청값을 직접 넘기는 경로는 이 관리자 설정 기능이었습니다.

GET 요청도 받아들이는 라우트

app/config/routes.php
array(
    '/admin/environment/boolean/toggle',
    'ANY',
    'admin@toggle_boolean_value'
),

app/config/routes.php에는 메서드가 ANY로 등록돼 있었습니다. 따라서 설정 변경이 GET으로도 실행됩니다. 관리자 로그인은 필요하지만, 별도로 찾은 CSRF 검증 누락과 함께 보면 관리자가 외부 링크를 여는 상황에서 요청이 전달될 수 있었습니다. SQL Injection과 CSRF는 원인이 달라 각각 보고했습니다.

로컬에서 확인한 순서

Docker로 분리한 테스트 환경에서 한 번에 큰 결과를 보려 하지 않고 동작을 나눠 확인했습니다. 먼저 컬럼명 자리에 넣은 SQL 표현식이 평가되는지, 그다음 조건절을 바꿀 수 있는지, 이어서 다른 테이블을 읽는 서브쿼리가 동작하는지 확인했습니다. 관리자 비밀번호 해시를 읽어 설정 테이블의 workspace에 기록하고 페이지에서 반영되는 것도 확인했습니다.

해시를 읽었다고 곧바로 해시로 로그인할 수 있다는 뜻은 아닙니다. 더 중요한 영향은 프록시 인증 설정을 바꿀 수 있다는 점이었습니다. 관련 값을 변경한 뒤 관리자 쿠키가 없는 별도 브라우저 세션에서, 선택한 프록시 헤더만으로 관리자 접근이 가능한 상태를 확인했습니다. 이는 로컬 검증 결과이며 모든 배포 환경에서 프록시 설정이 똑같다는 주장은 아닙니다.

검증을 분리한 이유 · 결과 요약
요청의 name → SQL 표현식 평가 확인
             → WHERE 조건 제어 확인
             → 다른 테이블 값 조회 확인
             → 프록시 인증 설정 변경 후 별도 세션 확인

공격용 전체 입력 문자열은 이 기록에 싣지 않았습니다. 공개 Advisory에 검증 범위와 영향이 더 자세히 적혀 있습니다.

남겨 둔 결론

문제의 시작은 $value를 안전하게 바인딩했는지가 아니라 $name을 누가 정하는가였습니다. 요청자가 SQL 구조에 들어가는 이름을 고를 수 있어 설정값 수정과 다른 데이터 조회로 이어졌고, 로컬에서는 프록시 인증 설정을 통한 비밀번호 없는 관리자 접근까지 확인했습니다. 공개 Advisory의 심각도는 High, CVSS 8.1입니다.

고친다면

허용 목록을 사용하는 형태
$allowed = [
    'registration_enabled',
    'auth_proxy_enable',
    // 실제 변경을 허용할 설정만 명시
];

if (!in_array($name, $allowed, true)) {
    throw new InvalidArgumentException('Invalid setting');
}

클라이언트가 보낸 문자열을 그대로 컬럼 이름으로 쓰지 않고, 서버에서 정해 둔 설정 키에만 매핑해야 합니다. 위 코드는 방향을 설명하는 예시이며 실제 허용 설정명 전체를 뜻하지 않습니다. 상태 변경을 GET에서 빼고 서버 측 CSRF 검사도 적용해야 이 경로의 전달 방식까지 막을 수 있습니다.
