HortusFox 관리자 화면에서 빠진 CSRF 검사

설정 변경 라우트가 GET도 받는 것을 보고, 폼의 토큰이 실제 요청 처리 과정에서 검사되는지 확인했습니다. 화면에 보이는 것과 서버에서 일어나는 일이 달랐습니다.

대상
HortusFox ≤ 6.2
심각도

폼에는 토큰이 있었는데

관리자 설정을 보는 중 app/config/routes.php의 ANY가 눈에 들어왔습니다. 값을 바꾸는 작업이 GET으로도 실행될 수 있다는 뜻입니다. 폼에는 @csrf 필드가 있어 처음에는 서버가 토큰을 검사하리라 생각할 수 있습니다. 그래서 실제 검사가 어디서 호출되는지 컨트롤러까지 따라갔습니다.

이 프로젝트의 CSRF 검사는 프레임워크 PostValidator에 들어 있습니다. Plants, Tasks, User 컨트롤러에서는 변경 작업 전에 이를 사용합니다. 그런데 AdminController에는 같은 호출이 없었습니다. 토큰이 HTML에 들어 있다는 사실과, 요청을 받을 때 토큰을 거절할 수 있다는 사실은 다릅니다.

검증이 연결되는 자리

asatru-php-framework / controller.php
if (
    (!isset($_POST['csrf_token'])) ||
    ($_POST['csrf_token'] !== $_SESSION['csrf_token'])
) {
    // validation failed
}

관련 코드는 vendor/danielbrendel/asatru-php-framework/src/controller.php에 있습니다. 위 코드는 비교 부분만 추려 쓴 것입니다. 관리자 작업에서는 이 코드까지 도달하지 않았으므로, 토큰이 없거나 틀려도 이 검증에 의해 거절되지 않습니다. 단, 관리자 로그인 자체를 건너뛴다는 의미는 아닙니다. 일반 사용자로 관리자 URL에 직접 접근하는 검사는 막혔습니다.

링크 하나로 요청되는 작업들

app/config/routes.php · 일부
array('/admin/environment/boolean/toggle', 'ANY', ...),
array('/admin/user/remove',               'ANY', ...),
array('/admin/api/add',                   'ANY', ...),
array('/admin/api/{token}/remove',        'ANY', ...),
array('/admin/api/{id}/toggle',           'ANY', ...),
array('/admin/cache/clear',               'ANY', ...),

설정 토글만의 문제가 아니었습니다. 사용자 삭제, API 키 생성과 제거, 캐시 초기화 등 상태가 바뀌는 관리자 작업이 같은 방식으로 등록돼 있었습니다. GET을 허용하면 브라우저에서 링크를 여는 동작도 요청이 됩니다. CSRF 토큰 검사까지 빠져 있으니, 로그인한 관리자가 외부에서 온 링크를 열었을 때 서버는 그 요청을 의도한 클릭과 구별하기 어렵습니다.

실제 브라우저에서는 어떻게 되는가

코드만 보면 ‘외부 사이트에서 요청할 수 있다’까지는 추정할 수 있지만, 세션 쿠키가 정말 같이 가는지는 브라우저 정책에 달렸습니다. 그래서 로컬 Docker 환경에서 관리자 계정으로 Chromium에 로그인하고, 다른 출처의 테스트 페이지에서 요청을 보냈습니다. 쿠키를 수동으로 붙여 만든 요청은 브라우저의 CSRF 동작을 보여주지 못하므로 사용하지 않았습니다.

요청 방식을 나눠 보니 결과가 달랐습니다. 일반 링크처럼 최상위 페이지 이동을 일으키는 GET에는 쿠키가 실려 작업이 실행됐습니다. 이미지 요청과 fetch에는 쿠키가 실리지 않았고, 로그인 후 시간이 지난 상태의 cross-site POST도 막혔습니다. DB 상태 변화까지 확인한 경로는 최상위 GET 이동이었습니다.

왜 GET에서만 재현됐나

Chromium 검증 결과
top-level cross-site GET   → cookie sent / action executed
cross-site image request   → cookie blocked
cross-site fetch           → cookie blocked
cross-site POST            → steady state에서 cookie blocked

세션 쿠키에 SameSite가 명시되지 않아 Chromium의 기본 Lax 정책이 적용됐습니다. 이 정책에서는 다른 사이트에서 시작한 요청이라도 최상위 GET 이동에는 쿠키가 포함될 수 있습니다. 반대로 이미지나 fetch처럼 페이지 내부에서 보내는 교차 사이트 요청에는 쿠키가 차단됐습니다. 로그인 직후 짧은 기간의 POST 예외는 있지만 안정적인 재현 경로로 잡지 않았습니다.

이 차이를 확인하지 않고 ‘모든 교차 사이트 요청이 통한다’고 적으면 실제 브라우저 동작보다 넓게 말하는 셈입니다. 이 보고서의 핵심은 관리자 세션이 있는 브라우저에서 링크 이동만으로 상태 변경이 가능하다는 점입니다.

이 문제가 닿는 범위

관리자가 로그인한 상태에서 외부 링크를 열면, 사용자 삭제나 API 키 변경처럼 서버 상태를 바꾸는 요청이 관리자 세션으로 처리될 수 있습니다. 인증이 없는 사람이 관리자 기능에 직접 들어갈 수 있다는 취약점은 아닙니다. 별도로 보고한 SQL Injection도 같은 GET 라우트에서 일어나므로 두 문제가 연결될 수 있지만, 빠진 검증과 SQL 문자열 조립은 각각 다른 원인입니다.

고친다면

처리 원칙
// 상태 변경은 POST 등 의도한 메서드만 허용
// 모든 관리자 작업에서 서버 측 CSRF 토큰 검증
// 쿠키에 SameSite, HttpOnly, Secure 속성 명시

상태를 변경하는 라우트에서는 GET을 받지 않고, 관리자 작업마다 서버에서 토큰을 검사해야 합니다. SameSite, HttpOnly, Secure 같은 쿠키 설정을 명시하는 것도 좋지만 토큰 검사를 대신하지는 못합니다. 화면에 필드를 추가하는 것만으로는 이 문제가 해결되지 않습니다.
