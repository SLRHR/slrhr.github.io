로그인할 때 다른 고객의 체크아웃이 옮겨진 문제

게스트가 로그인하면 진행 중이던 체크아웃을 계정에 이어 붙이는 기능을 읽다가, 넘겨받는 체크아웃이 정말 그 방문자의 것인지 확인하는 부분이 보이지 않았습니다.

대상
OroCommerce 7.0.4
분류
CWE-639 · CWE-863
확인
로컬 테스트 환경에서 재현
공개 기록
어드바이저리·CVE 없음
제보
이메일

로그인 뒤에도 장바구니가 이어지는 방식

쇼핑몰에서는 로그인 전에 시작한 구매 과정을 로그인 후에도 이어서 볼 수 있어야 합니다. OroCommerce도 로그인 요청에 담긴 체크아웃 ID를 읽어, 그 체크아웃을 방금 로그인한 사용자 쪽으로 옮기는 흐름이 있었습니다. 문제는 ID로 찾은 대상이 이미 다른 고객의 체크아웃일 때였습니다.

LoginOnCheckoutListener를 따라가 보니 ID로 체크아웃을 불러온 다음 소유자를 바꾸는 단계로 넘어갑니다. 존재하지 않는 ID인지는 확인하지만, 기존 소유자가 있는지와 현재 익명 방문자에게서 시작한 체크아웃인지까지 확인하지 않았습니다. 로그인 폼의 CSRF 토큰은 내 로그인 요청이 맞다는 것만 확인할 뿐, 그 안에 적힌 체크아웃 ID의 소유권까지 증명하지는 못합니다.

LoginOnCheckoutListener · 흐름을 줄여 쓴 예시
_checkout_id → CheckoutManager::getCheckoutById()
             → 체크아웃이 있으면 로그인한 사용자로 소유자 변경
             → 원래 소스를 바탕으로 새 체크아웃 생성
             → 기존 체크아웃 제거

예전 코드에는 있던 조건

관련 코드를 더 보다가 로그인 후 리다이렉트를 다룬 리팩터링 전후를 비교했습니다. 이전에는 체크아웃이 없거나 이미 고객·사용자 소유로 묶여 있으면 이전하지 않는 조건이 있었습니다. 7.0.4에서는 없는 ID만 걸러낸 뒤 소유자 변경 함수가 호출됐습니다. 이 차이가 실제 동작에서도 나타나는지 확인해 보기로 했습니다.

이전 조건과 7.0.4 조건 · 핵심만 발췌
이전:   체크아웃 없음 || 이미 고객 사용자 소유 || 이미 고객 소유 → 중단
7.0.4: 체크아웃 없음 → 중단
       그 외에는 로그인 사용자로 소유자 변경

코드 차이가 곧바로 영향의 증거가 되는 것은 아니라서, 서로 다른 고객에 속한 계정을 만들어 동작을 따로 확인했습니다.

깨끗한 환경에서 다시 확인

OroCommerce 7.0.4를 새로 설치한 로컬 환경에서 고객 A와 고객 B를 만들었습니다. A는 일반 쇼핑몰 화면과 API로 상품을 담고 체크아웃을 시작했습니다. B의 계정으로 A의 체크아웃을 직접 열면 처음에는 403이 나왔습니다. 이 상태가 정상적인 권한 경계였습니다.

다른 세션에서 B가 자신의 정상적인 계정과 CSRF 토큰으로 로그인하면서 A의 체크아웃 ID를 함께 보냈습니다. 로그인 후에는 A의 상품 정보가 들어 있는 새 체크아웃이 B 소유로 만들어졌고, B가 화면에서 열 수 있었습니다. 반면 A의 원래 체크아웃은 사라졌고, A는 새 체크아웃에도 접근하지 못했습니다.

로컬 재현에서 확인한 접근 결과
로그인 전  B → A의 체크아웃       403
로그인 후  B → 새 체크아웃         200 · A의 상품 정보 표시
           A → 원래 체크아웃      404
           A → 새 체크아웃        403

피해자의 로그인 정보나 세션은 사용하지 않았습니다. 다만 이 흐름에는 피해자의 체크아웃 숫자 ID를 알고 있어야 한다는 전제가 있습니다. ID를 별도로 알아내는 방법까지 발견했다고 적지는 않았습니다.

의도된 이전 기능과 비교했다

B 자신의 체크아웃 ID를 사용한 경우에는 정상적인 이어하기로 끝났고, 존재하지 않는 ID로는 상태가 바뀌지 않았습니다. 같은 익명 방문자에게 연결된 소유자 없는 체크아웃도 의도대로 이전됐습니다. 결국 모든 체크아웃 이전을 막는 것이 아니라, 이미 다른 고객 소유인 대상을 먼저 걸러야 하는 문제였습니다.

영향은 주문 완료나 결제 정보 탈취로 넓혀 적지 않았습니다. 제가 확인한 것은 B가 A의 상품 정보가 담긴 체크아웃을 열 수 있었고, A의 기존 체크아웃이 없어졌다는 데까지입니다. 로그인 중 체크아웃을 넘기는 순간, ID가 가리키는 대상의 소유권과 현재 방문자와의 관계를 확인해야 한다는 점이 이 기록의 핵심입니다.
